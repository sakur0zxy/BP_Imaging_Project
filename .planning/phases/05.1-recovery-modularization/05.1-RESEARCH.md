# Phase 5.1: Recovery Modularization - Research

## Research Goal

回答本 phase 的核心问题：
- 当前 recovery 层实际耦合点在哪里
- 什么结构最适合长期扩展到非 CS 方法
- 一次到位改造时，最稳的切分顺序是什么

## Live Code Findings

### 1. 当前恢复入口是单点耦合，但命名已经限制未来扩展
- `src/cs_recovery/run_cs_recovery.m` 是当前唯一恢复入口
- real/sim pipeline 都直接调用它
- 入口名、目录名、方法名都把恢复层绑定成了“CS 专用层”

### 2. 外部配置仍是扁平结构
- `config/default_real_config.m`
- `config/default_sim_config.m`
- `src/contracts/validate_real_config.m`
- `src/contracts/validate_sim_config.m`

当前 recovery 字段仍是：
- `method = '1d' | '2d'`
- `lambda1D`
- `lambda2D`
- `maxIter / tol / useFista / normalizeInput / verbose`

这会让后续新增非 CS 方法时很难继续扩展。

### 3. 1D / 2D 实现内部重复度高
- `src/cs_recovery/recover_1d.m`
- `src/cs_recovery/recover_2d.m`

两者都各自内嵌了：
- 输入校验
- 归一化
- FISTA 主循环
- objective 计算
- observed consistency 指标

真正不同的主要只有：
- 稀疏变换域
- 使用的 lambda
- 方法名

这说明 solver 与 transform 已经值得抽公共层。

### 4. 影响面不只 recovery 目录本身
当前至少以下区域会跟着改：
- `src/pipelines/run_real_data_pipeline.m`
- `src/pipelines/run_sim_data_pipeline.m`
- `config/default_real_config.m`
- `config/default_sim_config.m`
- `src/contracts/validate_real_config.m`
- `src/contracts/validate_sim_config.m`
- `tests/test_cs_recovery_smoke.m`
- `tests/test_real_pipeline.m`
- `tests/test_sim_pipeline.m`
- `docs/config_contract.md`
- `docs/pipeline_notes.md`

### 5. 这次不适合继续把 Phase 6 和恢复重构混做
如果现在直接继续 Phase 6 的恢复效果评测：
- 评测模块会建立在旧 `cs_recovery` 接口上
- 后面 recovery 重构时，analysis 又要跟着重改一次

因此更合理的顺序是：
1. 先完成 recovery 模块化
2. 再做 recovery evaluation / comparison output

## Recommended Target Structure

```text
src/recovery/
├── run_recovery.m                          % 恢复模块唯一入口；外部只认它
├── build_recovery_problem.m                % 统一恢复问题构造
├── prepare_recovery_config.m               % 补默认值、抽方法参数、校验配置
├── get_recovery_registry.m                 % 方法注册表
│
├── shared/
│   ├── resolve_observation_mask.m          % 统一 mask 解析
│   └── get_method_config.m                 % 读取 method 参数块
│
├── result/
│   ├── compute_recovery_metrics.m          % 统一指标
│   └── pack_recovery_result.m              % 统一结果输出
│
└── methods/
    ├── cs/
    │   ├── recover_cs_1d.m                 % CS 1D 恢复
    │   ├── recover_cs_2d.m                 % CS 2D 恢复
    │   ├── solvers/
    │   │   └── run_fista_sparse_recovery.m % CS 公共求解器
    │   └── transforms/
    │       ├── transform_azimuth_fft.m     % 1D FFT 变换
    │       ├── inverse_transform_azimuth_fft.m
    │       ├── transform_fft2d.m           % 2D FFT 变换
    │       └── inverse_transform_fft2d.m
    ├── interp/
    │   └── recover_interp_azimuth.m        % 未来插值法占位
    └── tv/
        └── recover_tv_2d.m                 % 未来 TV 法占位
```

## Locked Architectural Conclusions

- 恢复层应现在就升级成通用 `recovery/`，不要继续保留 `cs_recovery/` 作为正式结构
- 顶层只暴露 `run_recovery(...)`
- 正式方法名改为 `cs_1d`、`cs_2d`
- recovery 配置改为 `common + methods` 两层
- `solvers/` 与 `transforms/` 作为 `methods/cs/` 的内部细节下沉
- 恢复效果评测模块继续放在 `analysis/`，本 phase 不做

## Recommended Planning Split

### Wave 1
- 先冻结新的 recovery 外部契约：配置结构、方法命名、validators、docs contract

### Wave 2
- 建立 `src/recovery/` 骨架
- 迁移 `cs_1d / cs_2d`
- 抽公共 solver / transforms / result helpers

### Wave 3
- 切换 real/sim pipeline
- 更新测试与文档
- 删除旧 `src/cs_recovery/` 与旧 recovery API 引用

## Why This Is The Best Sequence

- 先定契约，再迁方法，最后切主流程，风险最小
- 能避免 pipeline 和 tests 一边依赖旧 API，一边依赖新 API 的半迁移状态
- 完成后再做 Phase 6 的 recovery evaluation，边界最清楚
